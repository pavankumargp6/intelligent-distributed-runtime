# IDR Service-Level Objectives

Status: Proposed for v1.0
Last updated: 2026-11-15

This document defines the service-level indicators (SLIs), service-level
objectives (SLOs), and measurement method for IDR.

The numbers below are **targets for v1.0**, not claims about the current
v0.x implementation. The current benchmark is a baseline, not an SLO.

## 1. Scope

The SLOs cover a single coordinator cluster with one or more worker
agents. Unless stated otherwise, measurements use:

- reference hardware: 8 vCPU, 16 GB RAM, local SSD, Ubuntu 24.04;
- coordinator and workers on the same LAN;
- no-op or short fixed-duration tasks;
- secure mode enabled;
- workloads generated by the repository benchmark harness.

HA targets apply only after Phase 6.

## 2. Service-level indicators

| SLI | Definition |
|---|---|
| **Submission success ratio** | `SUBMIT_ACK` responses divided by valid `SUBMIT` attempts, excluding client-side validation errors |
| **Submit latency** | Client-measured time from sending `SUBMIT` to receiving `SUBMIT_ACK` |
| **End-to-end latency** | Client-measured time from `SUBMIT_ACK` to a terminal `QUERY_RESULT` |
| **Queue wait** | Coordinator-measured time from enqueue to dispatch |
| **Execution time** | Worker-measured time from process start to process exit or timeout |
| **Recovery time (RTO)** | Time from coordinator process start to readiness with a populated WAL |
| **Durability** | Number of acknowledged submissions lost across a crash |
| **Worker-loss detection** | Time from worker death to its in-flight tasks being reaped |
| **Metrics availability** | Successful metrics scrapes divided by attempted scrapes |
| **Authorization rejection** | Invalid or missing credentials rejected divided by attempts |

## 3. SLOs

### 3.1 Durability and correctness

| Objective | Target | Measurement |
|---|---|---|
| Acknowledged submissions lost | 0 | Crash-point test matrix and kill -9 loops |
| Acknowledged terminal results lost | 0 | Crash-point test matrix |
| Non-idempotent tasks silently executed twice | 0 | Fault-injection test with crash between dispatch, accept, and result |
| Task ID reuse after recovery | 0 | Recovery test across snapshot and WAL truncation |
| WAL growth | Bounded by retention policy | Disk usage after 1M tasks |

Durability is a hard target. A single lost acknowledged task is a
release blocker.

### 3.2 Latency

| Objective | Target at v1.0 | Conditions |
|---|---|---|
| Submit latency p50 | < 10 ms | 1,000 submissions/s, 4 workers |
| Submit latency p99 | < 50 ms | 1,000 submissions/s, 4 workers |
| End-to-end latency p50 | < 50 ms | No-op tasks, 1,000 tasks/s, 4 workers |
| End-to-end latency p99 | < 250 ms | No-op tasks, 1,000 tasks/s, 4 workers |
| Queue wait p99 | < 100 ms | Offered load at 70% of measured capacity |

The current benchmark reports p50 17 ms and p95 19 ms end-to-end for
1,000 no-op tasks with 4 clients and 4 workers under WSL2. That is a
baseline, not a guarantee. The harness currently has one-second
resolution for some throughput calculations; Phase 3 replaces it with
nanosecond timers.

### 3.3 Throughput

| Objective | Target at v1.0 | Conditions |
|---|---|---|
| Sustained submissions | >= 3,000/s | p99 submit < 50 ms |
| Stretch submissions | >= 10,000/s | After Phase 3, documented hardware |
| Sustained completions | >= 2,000/s | No-op tasks, 8 workers |
| Queue capacity | >= 10,000 tasks | Configurable, bounded memory |

Throughput targets are tied to a published hardware and workload
description. A throughput number without that context is not an SLO.

### 3.4 Recovery

| Objective | Target at v1.0 | Conditions |
|---|---|---|
| Recovery time | < 5 s | 1M lifetime tasks, latest snapshot plus segments |
| Recovery memory | < 256 MB RSS | 1M lifetime tasks |
| WAL replay after snapshot | < 2 s | At most 100k records after snapshot |
| Worker-loss reaping | < 20 s | 10-second heartbeat timeout plus one tick |
| Dispatch timeout | 15 s | Assignment without `TASK_ACCEPT` |

### 3.5 Availability

| Objective | Target at v1.0 | Conditions |
|---|---|---|
| Single-coordinator availability | 99.5% monthly | Planned maintenance excluded |
| HA coordinator availability | 99.9% monthly | Phase 6, three-node cluster |
| Coordinator failover | < 5 s | Phase 6, leader kill |
| Metrics endpoint availability | 99.9% | Non-blocking endpoint |
| Metrics scrape latency p99 | < 50 ms | 1,000 scrapes/s |

Single-coordinator 99.5% is roughly 3.6 hours of downtime per 30-day
month. That is realistic for a process that must be restarted for
upgrades. HA raises the target to 99.9%, roughly 43 minutes per month.

### 3.6 Security

| Objective | Target at v1.0 |
|---|---|
| Unauthenticated commands accepted in secure mode | 0 |
| Replayed messages accepted | 0 within the replay window |
| Plaintext production mode | Not permitted |
| Parser crashes under fuzzing | 0 in the agreed fuzz duration |
| Secrets in logs | 0 |
| Release artifacts without checksums | 0 |

## 4. Error budget

For a 99.5% monthly availability SLO, the error budget is 0.5% of the
month, approximately 3.6 hours.

Policy:

- If more than 50% of the budget is consumed in a week, reliability work
  takes priority over new features.
- If the budget is exhausted, feature work pauses until the cause is
  fixed and a regression test exists.
- Durability violations are not budgeted. Any lost acknowledged task
  triggers a stop-the-line review.

## 5. Measurement plan

### 5.1 Benchmark harness

`tests/bench_runtime.sh` and `tests/bench_client.c` are the starting
point. Phase 3 will:

- use `CLOCK_MONOTONIC` and nanosecond timestamps for all latency and
  throughput calculations;
- run warmup plus at least five measured repetitions;
- report p50, p95, p99, p99.9, and confidence intervals;
- publish raw CSV and the exact hardware and software versions;
- separate submission throughput from completion throughput;
- measure coordinator CPU, RSS, fsync latency, and queue wait.

### 5.2 Production metrics

Phase 5 will expose Prometheus counters and histograms:

- `idr_submissions_total{result="ack|reject|error"}`;
- `idr_tasks_total{state="completed|failed|timed_out|unknown"}`;
- `idr_submit_latency_seconds` histogram;
- `idr_queue_wait_seconds` histogram;
- `idr_execution_seconds` histogram;
- `idr_queue_depth` gauge;
- `idr_inflight_tasks` gauge;
- `idr_workers{status="active|unavailable"}` gauge;
- `idr_wal_bytes` and `idr_wal_segments` gauges;
- `idr_recovery_seconds` gauge;
- `idr_auth_failures_total{reason=...}` counter.

### 5.3 Reporting cadence

- Per pull request: unit and integration tests, fuzz smoke test.
- Nightly: crash matrix, 24-hour soak, benchmark regression.
- Per release: full benchmark report and SLO summary.
- Monthly: review SLO compliance and error-budget consumption.

## 6. Known current gaps

The following v0.2 behaviors prevent the SLOs above from being met:

- the metrics endpoint can block the event loop;
- in-flight capacity is fixed at 64 and the worker pool at 16;
- a worker that accepts a task but cannot report a start failure (for
  example, the coordinator is unreachable) leaves the task in flight
  while the worker keeps heartbeating;
- the benchmark harness uses one-second resolution for throughput;
- there is no HA;
- there is no TLS.

WAL growth and duplicate non-idempotent execution are no longer listed:
v0.2 bounds the log with snapshots and segments, and uncertain
non-idempotent outcomes become `TASK_UNKNOWN` instead of being retried.

These are tracked in `docs/ROADMAP.md`.

## 7. Review

SLOs are reviewed at the end of each phase. Targets may change if
measurement shows they are unrealistic, but a target must not be lowered
merely because the implementation has not met it. Any change must be
recorded in this document with a date and rationale.
